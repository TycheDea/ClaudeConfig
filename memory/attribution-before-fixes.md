name: attribution-before-fixes
description: A mechanism read off code or arithmetic is not a cause until a measurement attributes the effect's magnitude to it; bundled changes are credited separately
metadata:
  type: feedback
---

Fires when a cause was established on paper (a code read, a capacity calculation) and a fix — or an out-of-scope routing ("pre-existing", "the renderer's") — follows before any measurement attributes the effect's magnitude; when one commit lands two changes and a single before/after number credits the pair; when adopting a candidate while an earlier one stands rejected on principle; when near-exhaustion of a resource is read as the binding constraint.

**Why:** five fixes and a GPU regeneration were spent on a grid stamp that owned 1–23% of the sign changes; a bundled weld was credited for a component-count fix, A/B'd alone at zero contribution and deleted; a "successor" operator agreed with a rejected one to within 1% and inherited its rejection; an 88%-exhaustion statistic drove an 11× grid refinement that was scale-invariant — the real defect was optimizer objective ≠ acceptance test.

**How to apply:**
- A code read proves a mechanism exists — never that it is *the* mechanism, nor how much it owns. Run the attribution first (partition the observed effect; prefer a statistic that can read 0%); it is cheaper than the fix because it needs no new correct behavior.
- n failed fixes on one premise are one refutation of the premise; the next spend goes to attribution, not candidate n+1.
- Two changes in one commit are two hypotheses; measure each alone before crediting either, or say in the commit that isolation was impossible.
- Disowning a defect is also an attribution and owes the same measurement.
- A rejection on principle creates a permanent comparator: keep it runnable, measure every successor's agreement with it (IoU/diff) before adoption; matching output inherits the rejection, and check each gate can even express the failure the principle names.
- Saturation is a ratio; before enlarging a resource, check the ratio at 2×/4× — scale-invariant means the constraint is elsewhere, usually a mismatch between what the optimizer maximizes and what the acceptance test measures.
