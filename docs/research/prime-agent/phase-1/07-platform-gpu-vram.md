**Baseline B:** user-authorized Prime Intellect PRIME Agent `v0.7.0`, commit `be9e2fa0714e7cd1c6bd9bdb1b554d2cc6550387` (tree `0625a8fd0550a8de7ff05e8d9248e75563e5b520`). Public read-only evidence only; no host probe, acquisition, install, account, container, model, renderer, benchmark, or GPU execution.

## Central verdict

**SOURCE-ONLY INTERMITTENT-HOST FIT: INSUFFICIENT EVIDENCE.** B's normal provider-backed path is control-plane software and declares **no local GPU/CUDA requirement**: the client, detached supervisor/catalog/workers, Python kernel, rollouts, and refinement run locally, while model weights/inference run behind a selected HTTP provider. That placement can avoid Vordar's local heavy-GPU lane. It does not establish coexistence: no CPU/RAM/state-growth totals, full installed/download size, end-to-end CPU-architecture matrix, Pi footprint, or practical VRAM measurement is declared; WSL2 is unnamed; and native Windows has no supported installer path plus an exact-source kernel-venv path defect corroborated on version 0.7.0. [S1-S9][P2]

Docker is **not** assumed. Core B has no Docker/OCI/Compose artifact or launcher and runs same-user shell/IPython unsandboxed. Docker appears only in optional **remote** Prime platform sandboxes/pods, reached through an unpinned separately installed `prime` CLI; the optional same-host sandbox example instead names Linux bubblewrap/macOS `sandbox-exec`. [S10][P2]

## Compute placement and coexistence boundaries

| Plane | Local on host | Remote/optional | Coexistence consequence |
|---|---|---|---|
| Pi control | Exact processes/resources unknown in this audit. | Its selected model may be remote; not established here. | Must remain independently resident/control; no quantitative headroom proof. |
| Prime client/daemon/worker/kernel | Node client, supervisor, catalog, root workers, Python kernels/forkserver, shell children; `~/.prime/agent`, project `.prime/agent`, OS temp. | Provider inference/weights and optional MCP/traces. | Source imposes no CPU/RAM/process quota; recursive concurrency can multiply local workers/kernels and remote requests. |
| Prime rollout/refinement | Orchestration, transcript/harness writes, optional metric/tool commands. | Model calls; optional hosted eval/training/storage/sandbox/tunnel/pod. | Hosted compute consumes no declared local GPU, but still uses CPU/RAM/network/state. |
| Local model | Separate operator-owned server/cache/weights. | N/A. | Heavy local GPU job; no B admission control or VRAM budget. |
| Renderer/visual | External Vordar renderer/capture and retained frames unless separately hosted. | Vision provider sees submitted stills; optional external render service is not B. | Rendering stays a heavy local GPU job; remote inference is not counted against local VRAM. |

**Isolation map.** Prime intends global/project state under `~/.prime/agent` and `.prime/agent`, Prime-named IPC, and `auth.json`; do not alias those paths to Pi. Isolation is incomplete: both run as the same OS user, inherit shared environment/PATH/provider keys, use shared OS temp (including inherited `pi-extensions` naming) and filesystem, and have unrestricted subprocess/network access. Prime retains `PI_PACKAGE_DIR`, `PI_OFFLINE`, `PI_SKIP_VERSION_CHECK`, and `PI_SHARE_VIEWER_URL`; simultaneous Pi/Prime values can cross-affect Prime. No credential broker, cgroup/job quota, port allocator, GPU lock, or cross-harness shutdown coordinator exists. [P2][P5]

**One-heavy-GPU-job rule.** With hosted model/eval/training, Prime's local control plane may coexist while the Vordar renderer owns the sole local heavy lane. A local model, self-managed `prime-rl`, model/weight job, or GPU-backed external visual tool must instead be serialized with Pi and rendering. PRIME does not enforce this project rule; phase 2 needs an external admission check that inventories child processes and GPU owners before launch. Remote GPU service use is reported separately and never counted as local capacity.

## Shutdown, abrupt loss, and restart ordering

1. **Orderly Prime stop:** stop/admit no new heavy external work, let or cancel the in-flight episode/refinement, then `prime-agent shutdown`; source stops workers/children/kernels, catalog, and supervisor. Closing only the TUI can detach and leave work resident. Pi has no B-defined relative stop order and must be checked separately. [S1][S8]
2. **Abrupt process/host loss:** command journals can yield completed/`uncertain`, but session/harness/checkpoint writes and provider/tool side effects are not transactionally closed. Kernel namespace, queued work, temp images, and in-flight remote outcome can be lost or ambiguous. Machine-off safety is therefore **unknown**, not supplied by Docker. [P2][P4][P5][P6]
3. **Power-on order from B:** mount/validate persistent Prime state and credentials/network; start a Prime CLI, which creates supervisor → catalog/worker → loads session/global+local harness → lazily restores/provisions Python kernel/forkserver → reconnects provider/optional services. There is no OS boot service/container. Cross-harness order is **unknown**: B neither starts nor validates Pi, so phase 2 must start/verify Pi control and Prime separately before any heavy job or retry. [S8][P2]
4. **Immediate retry:** reconcile `uncertain` command/provider/tool/refine outcome and surviving bytes first; do not replay an episode or GPU job by assumption. Missed schedules are not replayed as completed work. [P4][P5]

## Phase-2 host-probe and recovery gaps

No probe is authorized here. Before coexistence can be called fit, a later user-approved phase must record native Windows **and** WSL2 separately: OS/build/distro, CPU ISA/cores, filesystem/mount and temp semantics, shell path, Node/npm/uv/Python exact versions, PATH/env collisions, and whether B's Windows kernel defect is still present in the acquired immutable bytes. It must measure (not estimate) idle and loaded Pi versus Prime process trees, CPU, peak RSS, state/temp growth, complete install/download bytes, sockets/pipes/ports, credentials/egress, and local GPU model/VRAM/driver/CUDA ownership for each selected workload.

The recovery gate must exercise orderly shutdown and abrupt client/worker/host-death equivalents with downtime, then restart Pi and Prime independently in the order above; inspect exact session/harness/checkpoint bytes, in-flight disposition, orphan processes, same/new-ID retry, port/temp/state/credential separation, and a deliberately broken red proof. GPU probing, if later approved, must serialize renderer, Pi/Prime local models, self-managed training, and any other heavy job and demonstrate rejection of overlap. Until those checks pass, simultaneous residency is only architecturally possible—not evidenced safe or adequately sized.
