# Phase A1 — Tiling PBR Material Generator (subplan)

Source: `zesty-bubbling-acorn.md`, Plan A / Phase A1 (StableMaterials primary).
This file breaks that single phase paragraph into 7 single-agent tasks,
ordered by dependency. The orchestrator dispatches one agent per task,
verifies with the given command (never a GUI), commits on green, and strikes
the checkbox.

Tiers are the cheapest model that can do the job: **haiku** = mechanical
download/run/verify; **sonnet** = ordinary scripting/config/research;
**opus** = hard integration carrying real design/engineering risk (here:
the new Rust bin, per user ruling — see Divergence 2).

**Revision note:** this subplan was first written against a pre-rebase base
that lacked `bake_textures.mjs`, VQ-C5's DDS-manifest-freshness lint, and
offscreen feature-gating. `ai-pipeline` has since been rebased onto
`docs/mastery-skills`, which carries all three. This revision re-reads the
actual current state of `bake_textures.mjs`, `content_lint.rs`, and
`client/vordar-client/src/ground.rs`, incorporates three user rulings
(resolution strategy, bin tier + feature gating, bake step restored), and
flags one new wall the rebased base revealed (`texconv.exe` absent).

`C:\tools\StableMaterials\venv\` (new), not `C:\tools\TRELLIS\venv`.

venv's `huggingface-cli.exe`* for the weight download (A1.2) is still fine —

package install into that venv.

## Divergences and rulings (flagged per project policy — not silently patched around)

1. ~~`bake_textures.mjs` does not exist~~ — **resolved by the rebase.**
   The first pass of this subplan correctly identified that
   `scripts/asset-pipeline/bake_textures.mjs` and VQ-C5's DDS-manifest-
   freshness lint existed only on the (then-unmerged) `docs/mastery-skills`
   branch. `ai-pipeline` has since been rebased onto that branch, so the
   full pipeline is now live here: `bake_textures.mjs`'s `ground <dir>` mode
   (texconv → `BC7_UNORM_SRGB` albedo, `BC5_UNORM` normal, a composed
   `_mr.dds` via a `0r01` swizzle of the roughness map) plus a
   `manifest.json` (`{source, images: [{slot, file, source, sha256}]}`);
   `content_lint.rs::material_textures_have_fresh_sidecars` (VQ-C5) asserts
   that manifest exists, that its recorded `sha256` matches each source
   file's actual current hash, and that every listed `.dds` sidecar exists
   on disk; `client/vordar-client/src/ground.rs::load_ground_material`
   prefers the `.dds` sidecar per map slot (`find_dds`) and only falls back
   to the raw JPG/PNG source (`find_src`) if no sidecar was baked.
   **A1's flow is restored to what the campaign plan originally described**
   (task A1.6 below): `gen_material.py` → `bake_textures.mjs ground` →
   content-lint (VQ-C5) → offscreen render → vision review.

2. **The vision-review "plane render" needs one small new Rust bin** —
   confirmed and **tiered opus** per user ruling (supersedes this
   subplan's earlier sonnet call). `client/vordar-client/src/bin/render_material.rs`
   (A1.5, below). A0's turntable tool
   (`smirk/engine-renderer/src/bin/turntable.rs`) only accepts a `<glb>` —
   ground materials have no glb — and can't be extended in place: it lives
   in `engine-renderer`, which sits below `vordar-client` in the dependency
   graph, and `ground.rs`'s `load_ground_material`/`generate_ground` (what
   actually knows how to turn a texture directory into a lit mesh) live in
   `vordar-client`. A new bin is architecturally the only place this can go.
   It must respect the same feature-gating turntable does: `engine-renderer`'s
   `offscreen` module is `#[cfg(feature = "offscreen")]`
   (`smirk/engine-renderer/src/lib.rs:18-19`), and turntable's own
   `[[bin]]` entry carries `required-features = ["offscreen"]`
   (`smirk/engine-renderer/Cargo.toml:18-20`), run via
   `cargo run -p engine-renderer --release --features offscreen --bin turntable`.
   `vordar-client` currently only pulls `engine-renderer`'s `offscreen`
   feature and `wgpu` in as **`[dev-dependencies]`** (for
   `tests/ground_render.rs`) — `[[bin]]` targets don't see dev-dependencies,
   so this task adds vordar-client's own forwarding feature
   (`offscreen = ["engine-renderer/offscreen"]`) and moves `wgpu` to
   `[dependencies]`, gating the new bin with its own `required-features`,
   exactly mirroring turntable's pattern one crate over. This Cargo-graph
   plumbing across two crates' feature sets is real, non-mechanical risk —
   consistent with the opus retier.

3. **Resolution: superseded by user ruling.** This subplan's first pass
   defaulted to a hard 1024 generation cap + plain Lanczos upscale to
   `--size`, reasoning that StableMaterials' native training/generation
   resolution is 512×512 and a raw 2048 request (4x native) risks
   repetition artifacts and VRAM pressure. **The user overruled the plain-
   Lanczos part**: generation still natively caps at 1024 (2x native — the
   standard safe "hires" ceiling), but reaching `--size` beyond that is now
   a **tiled/seam-aware diffusion upscale**, not a resample.

   **Integration decided: whole-canvas SDXL img2img in the same
   StableMaterials venv/process, not ComfyUI.** Two options were weighed:
   - *ComfyUI SDXL img2img (tiled, e.g. an "Ultimate SD Upscale"-style
     node graph):* rejected. Vanilla ComfyUI (A0.1's install) ships no
     tile-split/seam-blend node — that functionality lives in third-party
     custom node packs never installed here. Building it would mean either
     a new custom-node install (real new scope for a phase meant to stay
     small) or hand-rolling tile-crop/feather-blend logic in Python. It
     also means running a second server process and shipping the 1024
     image across an HTTP hop mid-script — more moving parts for a CLI
     tool that should stay simple.
   - *Whole-image SDXL img2img in-process (chosen):* `diffusers` (already
     being installed for StableMaterials, A1.3) ships
     `StableDiffusionXLImg2ImgPipeline` — no new package. It loads directly
     from the **already-downloaded, already-cleared** `sd_xl_base_1.0.safetensors`
     (`C:\tools\ComfyUI\ComfyUI\models\checkpoints\sd_xl_base_1.0.safetensors`,
     A0.2) via `from_single_file`, so this needs no new download and no
     new license-ledger entry (SDXL base is already `Cleared` in
     `content/source/CREDITS.md`). Crucially, **doing the whole 2048×2048
     canvas in one pass sidesteps the seam problem tiled diffusion exists
     to solve** — tile-splitting introduces boundary artifacts precisely
     *because* it processes disjoint regions; a single coherent denoising
     pass over the whole latent has no boundary to seam. VRAM at that
     canvas size is handled by `diffusers`' own built-in memory APIs —
     `pipe.vae.enable_tiling()` (tiles only the VAE encode/decode, not the
     UNet's denoising loop, so it doesn't reintroduce the seam problem) and
     `pipe.enable_attention_slicing("auto")` — both standard, documented
     calls, not research code.
   - Low `strength` (starting point: `strength=0.35`, `num_inference_steps=40`,
     `guidance_scale=7.0`, same prompt text as the base generation) anchors
     the img2img pass structurally to the already-coherent 1024→Lanczos-
     upscaled-to-target init image, adding authentic high-frequency detail
     instead of hallucinating new composition — the standard "SD Upscale"
     community recipe, well past 1x SDXL's own native resolution but
     reliable specifically *because* it's img2img, not txt2img, at that
     scale.

   **Only the albedo (`diff`) gets this treatment.** Normal (`nor_gl`) and
   roughness (`rough`) are Lanczos-resized instead — stated explicitly per
   the ruling's own instruction to handle them with "a correct method":
   a diffusion pass (even low-strength) perturbs per-pixel RGB values, and
   for a normal map those values *are* a tangent-space unit vector — any
   generative hallucination of "detail" there produces a geometrically
   invalid direction, not a plausible one. Roughness is a physical scalar
   whose spatial pattern should track the albedo/normal's actual surface
   variation, not gain independent generative detail uncorrelated with
   either. Deterministic resampling is the correct method for both; only
   color/albedo detail benefits from (and tolerates) generative upscaling.

4. **Upscale scheme reworked post-A1.6 (user-approved 2026-07-18):**
   vision review found 1024-native generation washes out StableMaterials'
   crack structure (crisp only at its 512 training resolution) — three-seed
   sweep confirmed, not seed luck. `gen_material.py` now always generates
   native at 512 and reaches larger sizes via chained ×2 whole-canvas SDXL
   img2img hops on the albedo; the NATIVE_MAX/1024 clamp scheme is deleted.
   Preview lesson: only 512-native previews predict final structure.
   **2048 standard (user rulings 2026-07-18, in order):** a 1024 cap was
   briefly ruled while the 2048 whole-canvas hop thrashed WDDM paging
   (~28+ min/material); `enable_model_cpu_offload()` on the SDXL pipe fixed
   it (3m49s total) and the user lifted the cap — 2048 default, offload
   mandatory on 12 GB.
