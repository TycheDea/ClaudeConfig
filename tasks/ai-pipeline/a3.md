# Phase A3 — Prop Generator (image → 3D) (subplan)

Source: `zesty-bubbling-acorn.md`, Plan A / Phase A3, **revised 2026-07-19
under the user's strict NC ruling**: NC-licensed tools must never touch the
production asset path, even as build tools (consistent with the TRELLIS.2
block); eval-only use of NC tools remains allowed, but their outputs never
ship. TRELLIS 1's glb texture bake hard-imports `nvdiffrast.torch`
(NC-licensed), so **the production backbone is now Hi3DGen**
(`Stable-X/Hi3DGen`, MIT, nvdiffrast/kaolin/flexicubes stripped by its
authors "for commercial use"), which outputs *geometry only* — a
clean-licensed texturing stage becomes part of the chain. TRELLIS 1 is kept
as a single eval-only baseline run (outputs held under `target/`, never
`content/`).

This file breaks the phase into 15 single-agent tasks plus 1 contingency task
(not run by default), ordered by dependency. The orchestrator dispatches one
agent per task, verifies with the given command (never a GUI), commits on
green, and strikes the checkbox.

Tiers are the cheapest model that can do the job (user ruling 2026-07-18 — no
opus): **haiku** = mechanical download/run/verify; **sonnet** = ordinary
scripting/config/integration; **fable** = design-risky work (here: the
texturing strategy, the Blender cleanup heuristics, and the
candidate-selection judgment).

**Shell discipline (all tasks): FOREGROUND commands only.** Background shells
die silently on this box (repeated prior occurrences). Every long command gets
an explicit shell timeout (≤600000 ms) and must be **resumable** — re-running
the same command skips stages whose outputs already exist rather than starting
over. Nothing batches more than ~6 min of GPU work into a single command: the
candidate loop runs one seed per foreground invocation. The ComfyUI server is
launched as a detached OS process via `Start-Process` (never a backgrounded
shell), polled on `/system_stats`, and stopped with `Stop-Process` when the
task ends (A2.3 precedent).

Governance: Hi3DGen is already **Cleared** (MIT) in
`content/source/CREDITS.md`'s "AI pipeline models" table, and its weight
repos' licenses are now independently verified (facts section below); SDXL
base and FLUX.1-schnell (concept-image options) are Cleared; TripoSG
(contingency rung) is Cleared. A3.3 brings the ledger into line with the
strict ruling **before** any Hi3DGen generation (TRELLIS 1 → eval-only, weight
rows added) — the ledger is the hard gate and must not lag the ruling.

## Hi3DGen facts (researched 2026-07-19 — grounds the backbone switch)

From the actual repo (`github.com/Stable-X/Hi3DGen`: README, `app.py`,
`requirements.txt`) and HF model APIs, not the ledger one-liner:

- **Output is geometry only.** `app.py` runs
  `hi3dgen_pipeline.run(normal_image, seed=…, formats=["mesh"], …)` and
  exports via `generated_mesh.to_trimesh(transform_pose=True)` →
  `trimesh_mesh.export(path)`. No texture bake, no texture path at all — the
  clean-licensed texturing stage (A3.6) is required, not optional.
- **Pipeline stages:** BiRefNet background removal → StableNormal-turbo
  normal estimation (`torch.hub.load(…, "StableNormal_turbo",
  yoso_version='yoso-normal-v1-8-1', …)`) → normal-conditioned
  TRELLIS-derived geometry generation
  (`Hi3DGenPipeline.from_pretrained("weights/trellis-normal-v0-1")`, sparse
  structure + slat samplers, same knobs as TRELLIS).
- **Dependency list is NC-free.** `requirements.txt` verbatim contains
  diffusers/accelerate/triton (StableNormal), kornia/timm/transformers
  (BiRefNet), pillow/tqdm/scipy/trimesh/numpy/scikit-image/opencv/einops —
  **no nvdiffrast, no kaolin, no flexicubes, no diffoctreerast, no
  flash-attn** anywhere. README confirms the NVIDIA libs were deliberately
  removed. Mesh export is trimesh, not a differentiable rasterizer.
- **Attention backend is xformers** (README installs
  `xformers==0.0.27.post2`; the TRELLIS-derived modules use the same
  `ATTN_BACKEND` machinery). `app.py` sets `SPCONV_ALGO=native`, same as our
  TRELLIS runtime env. **The carried xformers-CUDA blocker therefore still
  applies — to the new Hi3DGen venv** (A3.1 installs the CUDA wheel there
  from the start) and to the TRELLIS venv only for the eval baseline (fix
  rides inside A3.11, its only consumer).
- **Weights (all three verified via HF API, license + size):**

  | Repo | Role | License (HF cardData) | Size |
  |---|---|---|---|
  | `Stable-X/trellis-normal-v0-1` | geometry pipeline | **mit** | 2.65 GB (4 safetensors + configs) |
  | `Stable-X/yoso-normal-v1-8-1` | StableNormal-turbo predictor | **apache-2.0** | 2.63 GB (unet/vae/controlnet fp16) |
  | `ZhengPeng7/BiRefNet` | background removal | **mit** | ~0.44 GB |

  StableNormal hub *code* (`hugoycj/StableNormal`, fork of
  `Stable-X/StableNormal`): Apache-2.0. Hi3DGen code: MIT. **Every license in
  the production path is MIT or Apache-2.0 — the strict ruling is satisfied
  end to end.** Total new download ~5.7 GB.
- **Torch/python:** README's tested recipe pins `torch==2.4.0` /
  `xformers==0.0.27.post2` / `spconv==2.3.6`. We build on the box's proven
  combo instead — Python 3.11.9, torch `2.7.1+cu128`, xformers
  `0.0.31.post1` (the CUDA cu128 wheel verified resolvable, see TRELLIS
  notes), spconv from the TRELLIS fork's local
  `spconv_cu128-2.3.8-cp311-win_amd64.whl` — because TRELLIS-architecture
  code already runs on exactly that stack on this machine. The README pin set
  (torch 2.4.0+cu124) is the evidenced fallback if 2.7.1 trips API drift.
- **VRAM:** not published. Largest single model is 2.65 GB and the stages run
  sequentially; a 12 GB fit is expected but **unverified — the A3.4 smoke is
  the check**, before any batch spend.
- **Install risks (flagged, with evidenced fallbacks):** (1)
  `requirements.txt` lists `triton`, which has no official Windows wheel —
  install without it first (TRELLIS on this box runs triton-free); if
  StableNormal-turbo actually demands it at runtime, `triton-windows` is the
  fallback. (2) spconv wheel is 2.3.8 vs the pinned 2.3.6 — accepted (it is
  the exact wheel TRELLIS runs on here); pin-matching from PyPI is the
  fallback if it misbehaves.

## Fixture prop: iron candelabra shrine (and why)

Of B3's prop list (chapel arch, broken column, candelabra shrine, stone
cross/stele, cypress, olive stump), the **iron candelabra shrine** is the one
that stress-tests every stage of the chain:

- **Metallic PBR** — the only prop class exercising the metallic channel end
  to end (now through *our* texturing stage → MR map → BC7 DDS bake).
  Rocks/stumps/stone would leave metalness untested until B3.
- **Thin features** — candle arms/stem stress the sparse-lattice resolution
  and the decimation budget; exactly the failure mode the TripoSG rung exists
  for. A blobby stone cross would pass without proving anything.
- **Mixed-material read** (iron + wax + stone base) stresses the concept
  stage's object legibility and is the sharpest test of the texturing
  strategy (A3.6) — three distinct material responses on one mesh.

If Hi3DGen fails on it, that is the decision-gate data A3 exists to produce —
the ladder runs on the *same* prop class, not an easier one.

## Divergences from the literal phase-spec wording (flagged per project policy)

1. **Backbone: Hi3DGen, not TRELLIS 1.** Forced by the user's strict NC
   ruling (2026-07-19): TRELLIS 1's only glb path bakes textures through
   nvdiffrast (NC). Hi3DGen was the plan's own first fallback rung and is
   fully clean (facts above). Consequence: the backbone outputs untextured
   geometry, so the chain gains a texturing stage (A3.6) the campaign
   paragraph never mentions — it is a required stage, not scope creep.
2. **"VQ-E1 zone-ref lint" is a misnomer in the campaign plan.** In
   `game/vordar-game/tests/content_lint.rs`, VQ-E1 is the *ability-VFX-beats*
   lint. The actual zone-ref gates for a prop are: `zone_visual_refs_load`
   (every zone prop glTF parses through the engine loader),
   `total_texture_memory_within_budget` (prop image slots counted), and
   `check_gltf_sidecars` (VQ-C5 — fresh DDS sidecars in `<name>.textures/`
   with matching sha256). A3.13 runs those by their real names.
3. **"Renders in the offscreen zone test" has no literal test.** No test
   renders zone props offscreen (`offscreen.rs` is synthetic;
   `ground_render.rs` renders ground only). The engine-side render gate is
   the **turntable contact sheet of the final glb** — the same
   `load_gltf_data` → static-mesh → IBL path zone props draw through — plus
   the unchanged full suite at the phase gate. Same resolution as A2's
   divergence 1: the suite never consumed asset files.
4. **Output format: `.glb`, not Poly Haven's `.gltf+bin`.** Existing props
   are fetched `.gltf`; generated props emit a single self-contained `.glb`.
   Both parse through the same loader and `bake_textures.mjs gltf` handles
   both — the zone `props:` entry just references the `.glb`.
5. **Concept model: SDXL base primary, FLUX.1-schnell alternate.** The plan
   allows either; SDXL is chosen as default (proven in this pipeline,
   cleared, ControlNet ecosystem available later). Schnell stays a per-prompt
   fallback if SDXL's object concepts read poorly — a workflow-JSON change,
   not a design change.

## Generation budget (user approves with this subplan — CLAUDE.md §8; nothing dispatches before approval)

Fixture prompt (P-C): "wrought iron candelabra shrine, standing votive candle
stand with melted wax candles, weathered dark iron, stone base, semi-realistic
dark fantasy, neutral studio lighting, 3/4 view, single object centered, plain
light grey background".

Wall-time basis: Hi3DGen's geometry stage is the same DiT/sampler
architecture and step counts as TRELLIS-image-large, which this box runs the
surrounding stack for at torch 2.7.1+cu128; it *skips* the texture bake
(TRELLIS's most expensive postprocess) and *adds* a one-pass StableNormal
prediction + BiRefNet matte (SD-sized fp16 models, seconds each) — estimated
~2–3 min per candidate, sanity-checked by the X2 smoke before any batch
spend. SDXL costs are A1/A2-measured on this box.

| ID | Run | Expected wall-time |
|---|---|---|
| D1 (download, no GPU) | Hi3DGen weights: `trellis-normal-v0-1` 2.65 GB + `yoso-normal-v1-8-1` 2.63 GB + BiRefNet ~0.44 GB (A3.2) | ~5.7 GB disk |
| X1 (exempt) | Single 512 concept preview, SDXL smoke of the new workflow (A3.7) | ~15 s |
| X2 (exempt) | Single low-step Hi3DGen sanity smoke on one test image — also the 12 GB VRAM fit check (A3.4) | ~1–2 min |
| G1 | Concept batch: 4× SDXL 1024×1024 candelabra concepts, seeds 0–3 (A3.10) | ~2 min total |
| G2–G5 | Hi3DGen full run per concept, 4 candidates (A3.10) | ~2–3 min each (~10 min) |
| T1–T4 (conditional) | SDXL texture passes, only if A3.6's chosen strategy uses diffusion (Blender-projection-only path is CPU/exempt) | ≤2 min per candidate (≤8 min) |
| E1 (eval-only) | TRELLIS 1 baseline: one full run incl. its NC texture bake on the winning concept — output held under `target/`, **never ships** (A3.11) | ~4 min |
| R1–R4 | Retry allowance: re-seed a failed concept/geometry/texture candidate, incl. fixture re-runs after A3.12's verdict | ≤3 min each |
| C1 (contingency, off by default) | TripoSG rung — only if A3.12 fails Hi3DGen on quality; adds a ~7 GB weight download (A3.C1) | ~5 min |

**Total nominal: ~16 min GPU (+≤8 min if diffusion texturing); ceiling
~40 min (excl. contingency rung).**
Exempt as seconds-scale/CPU per the plan's own rule: turntable renders,
Blender cleanup/UV/bake, gltf-transform, DDS bake, lint runs.

## Texture strategy log (filled by A3.6)

**Ruling (2026-07-19): Strategy 1 — Blender projection bake — wins;
implemented in `scripts/ai-pipeline/prop_texture.py`.** Evaluated first per
the task order on the A3.4/A3.5 smoke artifacts
(`target/prop-hi3dgen-smoke/T-seed0-steps8/` + the concept-equivalent input
`C:\tools\TRELLIS\assets\example_image\T.png`); it passed the turntable
gate, so strategies 2–3 were not run (the order rule: move past 1 only on
concrete failure evidence).

- **Method:** Smart-UV atlas on the decimated mesh; the concept image is
  planar-projected along the concept view axis (fitted to the concept's
  alpha bbox) and EMIT-baked into the atlas — CPU Cycles, 1 sample,
  deterministic, ~2 s at 1024². The projection passes through the mesh, so
  back faces receive the mirrored front read: the strategy description's
  "mirror-projection fill" falls out for free. Texels whose projection
  lands on transparent concept pixels fall back to the concept's mean
  opaque color, so overhang/occluded texels read as material, never black.
- **Projection axis, verified empirically:** mesh front = Blender -Y
  (glTF +Z). Both mirror directions were baked and turntabled; greenness
  correlation against the concept at the concept-matching view: -Y 0.179
  vs +Y 0.154, and -Y is also the glTF-convention front. Hardcoded
  (pipeline-deterministic); a per-prop violation would show in A3.12's
  turntable review as a mirrored texture.
- **Backside evidence (the honest-turntable gate):** 4-angle engine
  turntables (256² and 512², sheets under `target/prop-texture-eval/`) —
  the back view keeps the front's material read (wood browns on struts,
  greens on foliage masses, no white/black voids); side views stretch
  near-tangent texels but stay legible at game-camera distance.
- **Known weaknesses (accepted; A3.12 weighs them on the real fixture):**
  (a) mesh regions wider than the concept silhouette get flat mean-color
  fill (tan patches on the smoke's arm-end masses); (b) near-tangent
  surfaces stretch; (c) occluded geometry inherits front texels; (d)
  Smart-UV on a decimated generated mesh yields thousands of tiny islands,
  so the black atlas background can bleed at deep mip levels despite the
  8 px bake margin.

**Rejected options:**
- **Strategy 2 (SDXL multi-view retexture): not run** — only justified had
  strategy 1's backside failed, which it did not. It costs T-budget GPU
  rows, a ComfyUI server lifecycle inside the texture stage (VRAM
  sequencing against Hi3DGen's 11.5 GiB peak), an xinsir ControlNet
  download, and still needs the same projection/blend machinery
  afterwards. It remains the evidenced escalation if A3.12 fails the
  candelabra on backside/seam quality.
- **Strategy 3 (material-zone painting via StableMaterials/A1): not run**
  — zone segmentation on generated meshes is its own unsolved risk, and
  StableMaterials emits tileable materials, discarding the concept's
  spatial storytelling (soot, wax drips, weathering gradients) that
  projection preserves.

**Channels contract as implemented** (single material, three PNGs embedded:
base 1.6 MB, normal 1.7 MB, mr 0.2 MB; TEXCOORD_0 only):
- **basecolor** = the projection bake above, 1024².
- **normal** = real high-to-low Cycles bake `clean_hires.glb` → atlas UVs
  (tangent space, OpenGL +Y, cage extrusion 0.01 m, max ray 0.03 m),
  1024². Verified non-flat with per-island hires detail; a few speckle
  texels on thin strands where rays graze neighbouring geometry.
- **MR** = per-material-zone constants per the contract (iron metallic
  1.0 / rough 0.4; wax/stone metallic 0.0 / rough 0.7), zones classified
  per texel from the baked basecolor's sRGB value (smoothstep band
  0.24–0.34, darker = iron). **Scoped gap, flagged:** this strategy
  captures no real MR data — the value-threshold zoning is tuned to the
  candelabra palette (dark iron vs pale wax/grey stone) and will mislabel
  props whose metal is not the darkest material; the smoke mesh's dark
  wood crevices are mislabeled metal for exactly this reason
  (metal_fraction 0.13). A3.12 judges whether the iron/dielectric split
  reads on the real fixture.

## Decision log (filled by A3.12)

**Reviewed 2026-07-19** — all four contact sheets + concepts + frames viewed,
E1 baseline viewed, manifests and `texture_stats.json` inspected, embedded
textures extracted and measured.

**Outcome: (b)-variant — re-texture all four candidates; no winner named, no
new seeds, no GPU, ladder NOT triggered.** The batch fails criterion 2
uniformly, but the cause is a deterministic texture-stage integration defect,
not a seed or a backbone weakness — rerolling seeds would reproduce it
exactly, and the ladder (A3.C1) would too, since TripoSG feeds the same
texture stage.

**Root cause (verified, not inferred):** `prop_texture.py`'s
`concept_stats()` assumes an alpha-matted concept (it was developed on
`T.png`, which has alpha), but `gen_prop.py` stage 4 passes the raw RGB SDXL
`concept.png` — no matted intermediate exists anywhere in the chain
(BiRefNet's matte lives only inside the Hi3DGen process and is not saved).
With zero transparent pixels: (1) `concept_alpha_bbox_uv = [0,1,0,1]` (all
four `texture_stats.json`), so the mesh is projection-fitted to the full
frame instead of the object silhouette — thin iron members miss their dark
strokes and sample the studio background; (2) `fill_color` = mean of the
*whole image* = light grey `(0.64, 0.64, 0.63)`; (3) background texels count
as "opaque" so the mean-fill fallback never triggers; (4) the darkest=iron MR
zoning then runs on a washed-out basecolor — `metal_fraction` 0.17–0.20 on
concepts that are 50%+ iron. Measured: baked basecolor median luma 0.61–0.67
vs concept iron luma ≈ 0.22. Every candidate renders as white
porcelain/chrome (e.g. cand_3 `frame_02.png`: glass-white scrollwork, one
dark chrome strip on the column) — none of A3.6's *known* weaknesses
(mean-fill patches, tangent stretch, backside mirror) is even assessable
until the bake projects true colors.

### Second pass (post matte fix, 2026-07-19)

**Reviewed:** all four regenerated contact sheets + close frames

**Matte fix verified working.** All four `concept_alpha_bbox_uv` are real
sub-frame fits (e.g. cand_2 `[0.23, 0.77, 0.03, 0.97]`), `fill_color`s are

dielectric half now reads correctly batch-wide.

**New deterministic defect found: MR zoning double-encodes sRGB — all iron
renders dielectric.** `prop_texture.py` `new_image()` creates byte images
(`float_buffer` unset), so `base_img.pixels` returns sRGB-encoded values;
lines 213–215 assume scene-linear and re-apply `** (1/2.2)`. Effective
iron band is therefore sRGB 0.043–0.093, not the documented 0.24–0.34.
Measured on the shipped MR maps: mean metallic is exactly 0.000 for every
on-island texel with basecolor value ≥ 0.12 (incl. the whole documented
band); on-island metal fraction is 0.015–0.10 and concentrated in
near-black island-edge texels. The reported `metal_fraction` 0.17–0.23 is
~90% black atlas background, not iron. Consequence in the frames: every
iron member renders as a light pewter-grey dielectric (rough 0.7) — no
directional metallic response, cand_3 `frame_02`'s twisted column reads
silver-white where the concept is near-black. Criterion 2's iron-metallic
half fails for all four — again a texture-stage defect, not a seed or
backbone issue. With the correct band, 36–57% of on-island texels sit
below value 0.34 — the right order for concepts that are ~half iron, so
the one-line fix (drop the re-encode) restores the intended split.
