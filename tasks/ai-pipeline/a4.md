# Phase A4 — Character Generator (subplan)

Source: `zesty-bubbling-acorn.md`, Plan A / Phase A4, planned 2026-07-19 under
the strict NC ruling (2026-07-19: NC-licensed tools never touch the production
asset path; TRELLIS 1 is eval-only) and on the Hi3DGen backbone A3 proved.
Goal: generate a playable character mesh end to end — concept → geometry →
cleanup → texture → **rig to the canonical Mixamo-convention skeleton** →
attach the existing clip library → engine-ready glb passing the character
lints — with a decision gate after the first character before any further
race spends budget.

This file breaks the phase into 15 single-agent tasks plus 3 contingency
tasks (not run by default), ordered by dependency. The orchestrator
dispatches one agent per task, verifies with the given command (never a
GUI), commits on green, and strikes the checkbox.

Tiers are the cheapest model that can do the job (user ruling 2026-07-18 —
no opus): **haiku** = mechanical download/run/verify; **sonnet** = ordinary
scripting/config/integration; **fable** = design-risky work (here: the rig
transplant script, the turntable animation extension, the character texture
ruling, and the decision-gate judgment).

**Shell discipline (all tasks): FOREGROUND commands only.** Background
shells die silently on this box (repeated prior occurrences). Every long
command gets an explicit shell timeout (≤600000 ms) and must be
**resumable** — re-running the same command skips stages whose outputs
already exist. Nothing batches more than ~6 min of GPU work into a single
command: the candidate loop runs one seed per foreground invocation. The
ComfyUI server is launched as a detached OS process via `Start-Process`
(never a backgrounded shell), polled on `/system_stats`, and stopped with
`Stop-Process` when the task ends (A2.3/A3.7 precedent).

**Governance: the primary path needs ZERO new models and ZERO new
downloads.** Every model it touches is already Cleared in
`content/source/CREDITS.md` and already on disk: SDXL base (concepts),
`xinsir/controlnet-openpose-sdxl-1.0` (pose lock, downloaded in A0.4),
`xinsir/controlnet-depth-sdxl-1.0` (multiview texture, A0.4), the Hi3DGen
stack (A3.2), and Blender 5.2. New ledger rows exist only on the
contingency rungs (UniRig weight files, MPFB2) and are each rung's own
first step — the ledger never lags a download.

## Engine character contract (probed 2026-07-19 — the machine gates this phase closes against)

## Canonical skeleton + clip library (probed 2026-07-19 — the durable assets)

- On disk: `content/source/characters/mixamo/Character.fbx` (5.8 MB, the
  Mixamo-rigged VRoid body) + `clips/` with **11 FBX files**:
  `attack_cast, attack_heavy, attack_slash, death, dodge, hit, idle,
  jump, run, tpose, walk`. `mixamo_to_glb.py` skips `tpose` and renames
  `jump → leap`, so an engine glb built from this library carries **10
  actions** — a superset of the 6 lint slots. ("11-clip library" in the
  campaign plan counts the files; the deliverable is 10 actions.)
- **Bone names carry the `mixamorig:` prefix in both** `Character.fbx`
  (`mixamorig:Hips`, `mixamorig:Spine`, …) and every clip FBX (probed
  byte-level 2026-07-19). Clip fcurves target bones by exact name → any
  rig that keeps this skeleton's names and rest pose plays the whole
  library natively, with zero retargeting. This single fact drives the
  phase's rig design (below).
- `mixamo_to_glb.py` machinery (proven, produced the shipped
  `human.glb`): finger-bone prune with weight-merge into hands (65-bone
  Mixamo skeleton → ≤64-joint palette), socket bones `handslot.r/.l` +
  `head` as non-deforming children, clips stashed as NLA actions
  (exported via `export_animation_mode="ACTIONS"`), height 1.744 m +
  `FLOOR_TOP = -0.5` baked onto the armature object, 30 fps.
- **Units invariant:** the Character.fbx armature imports at FBX cm scale
  and the engine's weapon-socket path compensates for exactly that
  (`client/vordar-client/src/weapons.rs:204` — the socket matrix bakes a
  cm→m scale; only rotation+translation carry over). Any new rig script
  must keep the imported armature's own transforms untouched and move the
  MESH into the armature's space — rescaling or applying the armature
  transform breaks sockets silently.

  mapping matches exact names; prefix variants need care). This makes the
  MPFB2 rung concrete: a parametric CC0 body that is *born* near the
  Mixamo convention.

## The rigging wall, and the design that removes it

**Wall (verified, not vibes):** the campaign's "UniRig as auto-rigger →
attach the existing clip library" does not compose. The clips animate
bones by exact `mixamorig:` name against Character.fbx's rest pose;
UniRig emits arbitrary per-mesh skeletons with no convention control and
no retargeter. Bridging them would mean building a joint-mapping +
rotation-retarget layer — a fragile new subsystem that the plan's own
architecture note (skeleton convention + clip library are THE durable
assets, `tasks/character-direction-notes.md`) exists to avoid.

**Design ruling: don't generate a skeleton at all — transplant the
canonical one.** The skeleton is fixed by architecture; "rigging" a
generated mesh reduces to (1) fitting the canonical armature to the mesh
and (2) computing skin weights. Blender's automatic weights does (2) with
zero installs, zero GPU, deterministically. (1) is minimized at the
source: the concept stage pose-locks generation with ControlNet-openpose
conditioned on a stick figure rendered *from the canonical skeleton's own
T-pose joint positions* — the generated character is born matching the
skeleton's proportions and rest pose, so the fit is a near-rigid
alignment, not a deformation solve. Consequences:

- The whole clip library, socket machinery, finger-prune, and
  height-bake reuse `mixamo_to_glb.py`'s proven code paths unchanged in
  behavior (A4.4 factors them into a shared module — swap rule applies).
- UniRig demotes to the **skin-weights contingency rung** (A4.C1): if
  Blender bone-heat weights disappoint on generated meshes, probe whether
  `generate_skin.sh` accepts an externally supplied skeleton fbx (its
  cross-attention design is skeleton-agnostic in principle;
  **unverified** — the probe is the rung's first step and its go/no-go).
- MPFB2 stays the **mesh-source contingency rung** (A4.C2), per the
  campaign's own decision-gate wording ("AI look + auto-weight to Mixamo
  skeleton applied to MPFB2/MakeHuman bodies").
- Known residual risk (the phase's riskiest assumption): Blender's
  bone-heat solve can fail or bleed on messy generated geometry
  ("failed to find solution for one or more bones" on non-manifold
  input). Mitigations, in order: cleanup already decimates/de-floaters
  (A3.5 machinery); a voxel-remesh fallback inside `char_rig.py` for
  weighting only; then the UniRig-skin rung. The A4.3 smoke plus the
  first batch produce the evidence either way.

## Divergences from the literal campaign/spec wording (flagged per project policy)

1. **Mesh source: Hi3DGen, not TRELLIS 1** — carried from A3's strict-NC
   ruling (TRELLIS's only textured-glb path imports `nvdiffrast.torch`).
   TRELLIS remains the eval-only baseline (E1 row).
2. **Rigger of record: canonical-skeleton transplant + Blender automatic
   weights, not UniRig.** Forced by verified UniRig facts (arbitrary
   skeletons, no template/retarget path) + the clip-compatibility
   requirement; UniRig becomes the skin-weights rung. Evidence above.
3. **"Attach the existing 11-clip library" lands as 10 glb actions**
   (tpose skipped, jump→leap) — the committed `mixamo_to_glb.py`
   convention, superset of the 6 lint slots.
4. **`fix_glb_materials.mjs` drops out of the chain.** It repairs
   FBX-roundtrip material loss; this chain never roundtrips the mesh
   through FBX (the textured glb imports into Blender with materials
   intact and re-exports as glb). Its material convention — every shipped
   character is `metallicFactor=0, roughnessFactor=0.8` — is absorbed
   into the character texture contract instead (constant-dielectric MR,
   A4.6), matching all four existing race models.
5. **"Turntable + animation frames" requires new engine capability** —
   the bin is verified static-only, so A4.5 adds clip sampling. Same
   resolution as A2/A3's "no literal test exists" divergences: build the
   real gate, don't pretend one exists.
6. **The four races do not all generate in A4.** A3 precedent: the phase
   proves the machine on one fixture; production assets are the B
   campaign's. A4 adds one post-gate generalization proof (dwarf — the
   most proportion-divergent race) and defers elf/valkyrie to B4, where
   B1's themed descriptions exist. Rationale: un-themed elf/valkyrie
   candidates would be regenerated themed in B4 anyway — pure waste;
   the dwarf run uniquely buys chain-generalization evidence (stocky
   silhouette on the shared skeleton) that de-risks B4's batch.
   Architecture note: all races share the one skeleton + clip library,
   so race bodies are silhouette/bulk variants on canonical proportions
   (the current content already does this — every race normalizes to
   ~1.7 m) — the openpose lock stays canonical for all races.

## Amendment — SkinTokens auto-skinning (2026-07-22)

Blender bone-heat skinning in `char_rig.py` is replaced by SkinTokens
skin-only prediction (A1b adoption; audit + verdict in
`tasks/repo-study-shortlist.md`). The rig stage is now three
subprocesses: `char_rig.py fit` (skeleton transplant + mesh fit +
rigid bind → `fit.glb`) → `char_skin.py` (SkinTokens venv, skin-only
`use_skeleton`+`use_transfer` path, externally seeded — they ship no
seed control) → `char_rig.py finish` (canonical bone names recovered,
weights adopted, end bones trimmed, rig-quality gate, clips/height/
export unchanged). The weld/bone-heat machinery and its solver-warning
gate criterion are deleted; the weightless-verts gate and bleed stat
remain, computed on the adopted weights. The UniRig `generate_skin.sh`
skin-weights contingency rung is obsolete — SkinTokens is its
successor and now IS the skinning stage, with re-roll (not a fallback
skinner) on gate failure.

Findings that shaped the integration (verified on the VRoid body,
seed 42):
- The tokenizer round-trip drops non-deforming leaf bones VARIABLY
  (28 joints in → 22 out on one mesh, 25 on another), re-emits generic
  `bone_N` names, quantizes joint positions (~5 cm error at human
  scale, 256-level grid), and a chain-tip joint absorbs its dropped
  leaf (their Head lands at our crown). Nearest-position renaming is
  therefore impossible; the mapper descends both hierarchies in
  lockstep with min-total-distance sibling assignment, gated on
  distance-to-assigned-bone-segment.
- The engine socket bones (`handslot.r/l`, `head`) are among the
  dropped leaves — they are re-added post-skinning exactly as before
  and must never be trimmed (runtime-referenced: `weapons.rs:170`,
  `vfx.rs:260`, `sync.rs:231`, guardrail `content_lint.rs:196`). Only
  the three Mixamo end bones (`HeadTop_End`, `LeftToe_End`,
  `RightToe_End`) are trimmed for good, with any predicted weights
  folded into their parents first (generated skeletons are now
  25 joints; shipped `human.glb` stays 28 until regenerated).
- Two latent Blender pitfalls surfaced and fixed in `char_rig.py`:
  the FBX importer leaves a junk static pose that the shipped T-pose
  action used to mask (pose now reset explicitly), and importing a
  skinned glb creates a groupless bone-shape mesh that must not be
  joined into the weight source. Shape-keyed input meshes are rejected
  loudly (`me.transform` does not move shape-key data — silent
  geometry corruption otherwise).
